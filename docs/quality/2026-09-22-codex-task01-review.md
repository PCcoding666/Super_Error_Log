## 2. 阻断与返修项

### F1 · P1：自动预算不持久化，重启可重新获得预算

位置：`src/mobile/service.ts:79,408`；恢复链 `src/mobile/store.ts:82` → `src/mobile/service.ts:284`。

`autoRetryUsed` 仍只有进程内 Map，持久化任务和恢复逻辑没有预算字段或从调用证据重建预算。一次瞬时失败后在 queued 退避期重启，新实例会重新从零计数；重复重启可以让同一轮、同一阶段突破三次调用。

新增 `mobileRetryBudget.test.ts:137` 只对已失败终态重复扫描，没有停止实例并从相同数据目录重新创建实例，不能证明跨重启上限。

要求：真实 HTTP 调用之前先持久化占用预算，恢复沿用同一轮次。崩溃后无法确定是否发出的预约不能自动返还为免费次数。兼容旧任务，不能将历史证据不完整理解为无限新预算。

### F2 · P1：按异常重试计数，不等于按阶段实际调用计数

位置：`src/mobile/service.ts:407`；`src/mobile/vision.ts:199`。

当前以 job/question 为 key 统计 retryable 异常，没有按 inventory/transcribe/verify/ground 分阶段统计真实调用。正常的 verify → ground → verify 本身可调用 verify 三次；夹入瞬时失败后还可外层重试。

具体可达路径：verify 返回合法但不通过的内容检查 → ground 成功 → verify 503 → 自动恢复 → verify 仍不通过 → ground → verify。累计 **4 次 verify**；两次瞬时失败可达 **5 次**。移除适配器内部循环只修复简单失败路径的乘法，没有兑现“每阶段实际调用最多三次”。

要求：所有真实调用共用按轮次、工作单元、阶段的持久化计数，包括成功响应但内容未通过的校验调用。预算用尽保留最新证据并明确失败，不能把未完成检查变成通过，也不能为了凑计数直接删掉 grounding 能力。

### F3 · P1：旧任务容量尚未恢复完，就可以接收新照片

位置：`src/mobile/router.ts:69`；`src/mobile/service.ts:246,271,273`。

启动不等待首次恢复扫描。旧任务在异步持久化之后才逐个登记容量，而 HTTP 入口可先进入服务状态。让十个旧任务的首个恢复写入暂停，此时新上传仍可能拿到空账目的名额，随后旧任务恢复使占用超过上限。

`mobileAdmission.test.ts:384` 先等 health 报满额才上传，避开了该窗口，只证明了“最终登记”，没有证明“先登记再接收”。

要求：容量恢复完成前不得接受新增任务；可选择延后监听或关闭新增准入，但必须保持可解释的启动状态。容量建立后再处理旧任务，不能因某个模型调用挂住而永远无法结束启动。

### F4 · P1：停止后，已进入的执行链仍能发起下一次模型调用

位置：`src/mobile/service.ts:235,372,378,394`；`src/mobile/vision.ts:199`；`src/mobile/cloudAssembly.ts:30`。

`stop()` 只设置标志并清 watchdog；排队入口受保护，但已经挂起的 inventory/题目请求返回后，后续题目与 verify/ground 阶段没有重新检查停止状态。其他请求触发存储故障时也可能留下这条执行链。云端 close 仅关闭 HTTP/admin，没有停止并等待识别 worker。

要求：每次新模型调用之前检查生命周期状态；停止后允许安全收尾已有请求，但不得开启下一阶段、下一题或退避重试。关闭流程需要明确、可等待的后台收尾契约。存储错误保持 fail-closed，不改写成模型失败。

### F5 · P1：证书迁移与回滚说明不能按现有顺序安全执行

位置：`deploy/README.md:166,174`；执行者报告第 6 节。

报告要求先迁移证书、后部署新版；迁移却从 `/opt/super-error-log/current/deploy/systemd/super-error-log-caddy.service` 复制新增单元。旧版本不含该文件，本地基线 Git 树也只有应用单元。必须先暂存并校验新版发布物，再从明确的新版路径取配置，不能依赖旧 current。

回滚要求复制旧 Caddy 单元，旧单元指回 `/var/lib/super-error-log/caddy`，应用父目录仍为 0700，直接重新引入本次修复的故障。“旧证书目录还在”不等于 caddy 用户可访问。说明也缺少覆盖前备份实际线上单元的步骤。

要求：区分暂存发布物、证书迁移、应用切换；应用版本回滚不能撤销独立证书存储的安全边界。备份单元和证书账户资料，检查各步骤前置条件，失败即停止，保留旧目录且不降低学生资料权限。跨 UID 和真实证书维护验证继续列为生产待验收，不得以一次 curl 401 或末尾 20 行日志代替。

### F6 · P2：并发扫描仍可重复排队，绕过退避窗口

位置：`src/mobile/service.ts:282,286,311`；`tests/integration/mobileRecovery.test.ts:234`。

两次扫描可同时通过 queued/inflight 检查，各自在 await updateJob 后入队。第一份已经执行时，第二份 enqueue 只检查 queued，不检查 inflight，因此可留下重复队列项。第一份瞬时失败回到 queued 并挂 timer 后，第二份可立即运行，绕过退避。现有并发扫描测试是在 completed 之后执行，不能覆盖这个时序。

要求：恢复扫描和队列工作单元的执行权唯一；在未完成任务上用 barrier 重叠两次扫描，证明调用不重复、退避不提前、容量不重复、revision 不被无意义重写。

### F7 · P2：人工重试并不总能建立新预算轮次

位置：`src/mobile/service.ts:150,349,367,455`。

inventory 失败只释放容量，不清理旧预算；人工重试也没有新轮次。因此用户主动再试遇到一次 503 就可能立即失败，没有获得预期的新一轮自动重试。某一道题失败但其他题还在执行时，也会继承旧题预算；只有整个照片 finalize 时才统一清理。

要求：人工重试的新轮次由明确持久化迁移建立，不依赖整张照片到终态，也不通过删除全部历史计数实现。已完成阶段不重复执行，旧失败证据保留并关联原轮次。

### F8 · P2：新增测试留下后台写入，当前全量门禁失败

位置：`tests/integration/mobileAdmission.test.ts:431`、`:17`。

`vision.finish()` 只是释放异步 inventory barrier，测试随即结束。afterEach 只等 HTTP server.close 就删数据目录，识别 worker 尚可继续写任务和媒体。本次实际 ENOTEMPTY 与这个生命周期缺口一致。

要求：在删除临时目录前停止并等待 worker/timer/扫描收尾；关联 F4 的正式生命周期契约。不能靠增加固定 sleep、忽略 ENOTEMPTY、反复删除、skip 测试或只报告重跑成功解决。

## 3. 报告与执行边界

- 当前代码中 recorder 写入失败仍可穿透为存储失败，这一点是好的。对比基线，成功路径 recorder 原本就在模型 try/catch 外；执行过程一度移动后又恢复，应写成“保持既有语义、修复本轮回归”，不能算作额外修好的历史缺陷。
