# Workbuddy 开发任务 01：云端识别可靠性修复

> 执行者：Workbuddy 中的 Kimi K3。Codex 负责总架构、产品范围、验收与独立 code review；本任务不调用 Qoder，也不转交其他模型编写代码。实施采用先失败测试、再最小修复、再回归的顺序；完成后交回 Codex 审查，不自动上线。

**Goal:** 让已有云端识别服务在证书维护、长时间识别、服务重启和瞬时模型故障下行为可预测，不丢任务、不重复扣减容量、不无限自动重试。

**Architecture:** 保留现有单进程、逐题串行、最多十张未完成照片的架构。把 Caddy 证书存储与应用私有数据目录隔离；统一任务所有权、容量预约与释放；把模型调用的自动重试预算明确到同一任务、题目及阶段。

**Tech Stack:** Node >=24、TypeScript ESM、Express 5、Vitest、Caddy、systemd 239 / cgroup v1。不要借修复升级技术栈。

**Spec:** `docs/superpowers/specs/2026-09-17-iphone-cloud-recognition-design.md`；故障恢复的后续变更参照 `docs/PRODUCT_VALIDATION_REPORT.md` 及当前实现。旧文档与代码矛盾时列出差异，不自行删除已被用户接受的自动恢复能力。

### A. 隔离 HTTPS 证书目录，修复权限冲突

调查入口：
- `src/mobile/pairing.ts` 的 `PairingManager.open`
- `src/mobile/store.ts` 的 `privateDirectory/open`
- `deploy/README.md` 中 Caddy 的 XDG_DATA_HOME 和服务单元
- `deploy/systemd/`、`deploy/caddy/`、发布打包测试

已观察到的现象：应用启动把 `/var/lib/super-error-log` 改成 0700；Caddy 的证书目录却位于其下。部署说明用父目录 0750 和补充用户组解决访问，但应用下次启动又覆盖权限。2026-09-21 只读线上审查发现 Caddy 证书维护持续报 permission denied。

要求：
- [ ] 保留应用题目、照片、配对数据的私有权限，不用 chmod 777、全局可读或让 Caddy 以 root 运行来绕过。
- [ ] Caddy 使用独立私有存储目录，不再嵌套在应用会强制私有化的目录内。同步环境配置、systemd 写权限和部署说明，避免只修其中一处。
- [ ] 将真实使用的 Caddy 服务配置纳入可审查的版本控制；保持现有 443 入口与 TLS-ALPN 方式，不占用或修改原网站的 80 端口。
- [ ] 提供保留现有证书、账户信息、文件所有权的迁移及回滚步骤。不实际执行，不删除旧目录，不以重新签发成功代替正确迁移。

验收：
- [ ] 回归证明应用初始化与再次初始化不会破坏 Caddy 存储路径的权限前提。
- [ ] 发布包内服务配置与说明一致；Caddy 的运行用户、写目录和应用数据访问边界可检查。
- [ ] 如可在现有隔离 Linux 环境验证，用不同 UID 证明 Caddy 能读写其存储、不能读取应用私有数据。若不能执行，明确标记“跨用户权限与真实重启待部署验收”，不可用 macOS 同用户 mkdir 测试冒充。

### B. 修复任务恢复和容量计数

调查入口：
- `src/mobile/service.ts` 的 `resumeIncompleteJobs/drain/processInventory/processQuestions/finalize`
- `src/mobile/admission.ts`
- `src/mobile/router.ts` 的启动与准入接线
- `tests/integration/mobileRecovery.test.ts`
- `tests/integration/mobileAdmission.test.ts`

待验证的缺陷：首次整页任务只登记 inventory inflight，随后在同一调用内执行逐题识别；watchdog 按 question inflight 判断时可能将正常任务视作僵尸。恢复时只更新 jobId 集合、未真正预约容量；重复 finalize 可能释放其他任务的容量。

必须保持的不变量：
- 同一工作单元最多一个执行者，长请求仍是活动任务，不因跨过 60 秒就重置或重复排队。
- 每个未完成照片任务恰好占一个容量位；逐题重试不另算一张照片。
- 每个容量预约恰好释放一次；重复 finalize、恢复扫描、并发重试均不能重复扣减。
- 启动恢复必须先正确建立已有任务的容量账目，再接受新照片；达到十张时拒绝新增，但保留查询及幂等重放能力。
- 如果历史未完成任务已经超过十张，不删除或丢弃旧任务；允许它们继续处理，低于上限后再接收新照片。
- 停止或存储故障后，延迟回调不能继续发起模型工作。

先写出并观察失败，再修复：
- [ ] 用可控 barrier 或时钟，让逐题模型调用横跨多个 watchdog 周期；断言调用不重复、题目不被错误重置。
- [ ] 重复扫描同一任务不增加重复队列工作。
- [ ] 从持久化的十个未完成任务恢复，第十一个新任务被拒；一个旧任务终态后恰好释放一个名额。
- [ ] 多次 finalize 同一任务，不影响另一个仍在处理的任务所占容量。
- [ ] 并发重试同一照片的不同题目只占一个照片名额。
- [ ] 存储失败、关闭服务及重启路径不遗留错误容量、不删除原任务证据。

不要让测试实际等待 60 秒；不要只测孤立计数器，至少覆盖真实 service + admission 的组合。

### C. 统一自动重试预算，保留可恢复性

调查入口：
- `src/mobile/vision.ts` 的 `BailianMobileVision.call`
- `src/mobile/service.ts` 的自动重试分支
- `src/mobile/contracts.ts`、`src/mobile/store.ts` 的恢复及持久化记录
- `src/ai/chatClient.ts` 的超时与错误分类
- 现有 mobileVision、mobileRecovery 集成测试

待验证的缺陷：模型适配器内最多三次调用，service 外层再重试，导致清单最多六次、逐题同一失败阶段最多九次。

本轮目标策略：
- 同一逻辑识别轮次、同一题目及阶段，最多三次自动模型调用（首次 + 两次重试），不能跨层相乘。
- 预算耗尽后变为明确的失败状态，保留结果与人工重试入口；其他题目可以继续。
- 自动恢复和进程重启不能给同一失败工作无限刷新预算；不重复执行已经持久化完成的阶段。
- 用户明确发起人工重试可以开启新的轮次，但要保留旧轮次失败与调用证据。
- 不为了让测试变快擅自缩短生产的 30 分钟单次超时。本轮解决预算和恢复一致性；产品等待时长策略单独交架构师决定。
- 认证、权限、格式等非瞬时错误不能因新机制被无限自动重试。

先红后绿的测试至少包括：
- [ ] 使用真实适配器 + service，底层 HTTP 为合成失败响应；累计实际请求次数不超过三次，不能只 stub MobileVisionBoundary 就宣称预算正确。
- [ ] 一次失败后成功，不发生额外调用；持续瞬时失败后进入明确终态。
- [ ] 自动恢复/模拟重启不重置已消耗预算；已完成阶段不重跑。
- [ ] 人工重试的新轮次可执行，旧失败记录不被覆盖或删除。
- [ ] 无需真实 API Key，不访问真实模型，不依赖长时间 sleep。

### 本轮明确不做

不增加登录或多人账户，不做云同步与资料恢复，不做题干编辑、补题、重裁图 UI，不做延迟复习状态机，不更换模型或重跑十张真实照片，不改变人工放行策略。

这些是后续独立任务，不是被忽略。发现相关问题写入报告，不顺手扩张。

### Review Focus

1. 正常慢任务跨越多个 watchdog 周期，不能被当成僵尸。
2. 重启前已有满额任务，启动后不能暂时接受额外十张。
3. 重复完成/迟到回调，不能释放另一张照片的容量或继续发起模型调用。
4. 模型内部与 service 外层错误恢复组合，不能突破同阶段自动尝试上限。
5. 应用与 Caddy 以不同 UID 启动，权限不能只在部署瞬间正确。
