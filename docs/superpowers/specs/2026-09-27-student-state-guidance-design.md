## 第一部分：学生视角的一页体验（上传后 → 复盘）

> 周末晚上，我拍完这周的错题。

1. **我打开 App，直接看到「本周」。** 没有欢迎页。最上面一行告诉我：「3 道题等你确认 · 1 张照片没识别成功」。我知道今天该干什么。
2. **每张照片是一张卡。** 卡上有缩略图、一句大白话状态（比如「待你确认 3 道题」）、一句下一步（比如「点这里逐题核对」）。整张卡都能点，不用找小按钮。
3. **点进去，每道题也是一张卡。** 卡上写着「第 3 题 · 待你确认」或「第 5 题 · 有内容需核对」。已确认的题我可以先放着，先处理要核对的。
4. **核对一道题时，原图就在上面，识别结果在下面。** 我看一眼原图、再看识别内容，确认无误点「确认这道题」。AI 没把握的题会明说「AI 没把握，需要你多看一眼」，我看原图后可以决定放行还是留待核对。
5. **识别失败的只失败那一道/那一张。** 卡片上说「没识别成功，可以重试」，重试只重做失败的部分，不影响已确认的题。
6. **确认完，卡片变成「已确认 · 可去复盘」。** 我点一下就能跳到复盘。复盘中想看原图、想改复盘，都找得到入口。已确认的题不会消失在某层菜单里。
7. **断网、关 App、换网络都不怕。** 再打开时照片还在本机，识别进度接着走；断网时看得到上次保存的结果，并明确告诉我「现在离线」。

## 第二部分：现状盘点（真实代码依据）

### 2.1 现有状态词表 vs 建议状态词表

**照片/任务级**（`Domain/Recognition.swift` `RecognitionJob.statusTitle`，184–194 行；`ThisWeekView.photoStatusView`，146–174 行）：

| 现有内部状态 | 现有文案 | 建议文案（学生语言） | 建议主操作 |
|---|---|---|---|
| 未上传（`consentedAt == nil`） | 仅保存在本机，尚未上传（灰） | 还在本机，没上传 | 加入待识别（现有勾选+底部按钮，保留） |
| 上传中（`busyTasks`） | 正在上传到识别服务 + 真实字节进度 | 正在上传（保留真实进度条） | 等待；进度来自 `uploadProgress`（StudyStore 27 行） |
| 上传失败 | 上传待重试，照片仍在本机（红） | 没传上去，照片还在 | 重试上传 |
| `queued`/`processing` | 等待识别/正在查找题目/正在逐题识别（蓝） | 正在识别 | 等待；显示「已处理 X/N 道」真实计数（复用 `RecognitionView` 14 行逻辑） |
| `completed`，有待确认 | 待你确认 N 道题（橙） | 待你确认 N 道题 | 逐题确认（整卡跳第一道待确认题） |
| `partial` | 部分识别完成 | 部分完成：X 道可核对，Y 道失败 | 先核对可核对的；失败单独重试 |
| `interrupted` | 识别已中断（红） | 中断了，可以接着来 | 继续识别（复用现有 `RecoveryButton`） |
| `failed` | 识别未完成（红） | 没识别成功 | 重试这张照片（只重试对应范围） |
| 全部确认 | 已全部确认（绿） | 已全部确认（**仅当题目数 > 0 且全部真正 confirmed**；聚合规则见第五部分） | 去复盘 / 查看题目列表 |

现有五色语义（灰/蓝/橙/绿/红）**已存在且合理**（`ThisWeekView.swift` 144–145 行注释：「看到橙色就是你的活」），本设计沿用并补齐「整卡可点 + 每卡一句下一步」。**不用技术标签当引导**：现有 `candidateBox` 百分比 DisclosureGroup（`RecognitionView.swift` 67–72 行「左 30%，上 12%…」）是技术信息当内容的反例，建议默认折叠为「查看技术细节」或移入调试区。

**题目级**（`RecognitionQuestion.statusTitle`，148–159 行）：queued 等待识别 / processing 正在识别 / ready 待你确认 / needs_check 有内容需核对 / confirmed 已确认 / skipped 暂不处理 / failed 识别未完成。词表基本合格，建议仅两处调整：needs_check 在列表行显示为「需要你核对」（比「有内容需核对」更指向动作）；skipped 显示为「已跳过」，只可查看。**当前服务端没有恢复已跳过题的接口**（`src/mobile/service.ts` 223–250 行：confirm 仅支持 confirm/skip 且已确认题不可跳过；retry 仅接受 failed 题；`RecognitionClient.swift` 123–130 行为据）。M1 不伪造「恢复」按钮，恢复能力列为未来接口需求。相应地，M1 新增「稍后核对」**仅退出当前页面**（保留 ready/needs_check 原状态，不调用持久 skip）；既有持久「暂不处理」（skip）保留，但确认弹窗必须如实说明「跳过后当前版本不能恢复处理」。

## 第三部分：方案选择（针对方向 A 的结构）

### 方案一：原位重构 + 统一卡片组件（推荐）

保持三 Tab 与全部既有流程（导入→同意→上传→识别→确认→复盘→练习包）不动。引入两个组件：`PhotoStatusCard`（缩略图 + 状态徽标 + 一句下一步 + 整卡 NavigationLink）与统一的「下一步」聚合条。「本周」页改为按行动分区的列表：待你处理 → 识别中 → 已确认/仅本机。题目详情页重排为：原图 → 识别内容 → 需核对项 → 单一主操作区（按状态只出现一个主按钮）。

- 优点：复用所有已验证的状态机、门禁与测试资产；改动面可控；与 9-12/9-14/9-17 设计连续；最快让学生在真机上感到差异。
- 缺点：信息架构仍是「照片为中心」，题目跨照片的聚合视角要等 C。

### 方案二：新增「任务中心」首页替代「本周」

把首页改为跨照片的题目级待办流（所有待确认/待核对/失败题混排为一条队列），照片退为详情属性。

- 优点：最直接回答「下一步做什么」。
- 缺点：与「本周」现有的导入/同意/选择/连接职责冲突，等于把两个页面压成一个；确认流程天然以照片为单位对照原图，跨照片混排会让「对照原图」动作上下文频繁切换；改动面约为方案一的 2–3 倍，且需要重做 9-17 云端验收过的上传链路 UI。

### 方案三：线性向导式流程（否决）

把上传→确认→复盘做成强制顺序的分步向导。**R1 更正**：用户反对的是开屏欢迎页/教学式入门，不是清楚的分步任务流程——确认页「对照原图→勾选→确认」这类有真实状态支撑的分步流程是保留的。方案三被否决的真正原因是：它把学生锁进单一预设路径、掩盖识别的异步并发本质（一道题识别中时应能先处理已完成的题），并以流程编排替代真实状态呈现。否决。

**推荐方案一**，并在其组件层为方案二的题目级队列预留数据结构（照片卡的状态聚合函数天然是题目队列的子集），M3 归类时可在「复盘」页内提供题目级分组视图，无需推翻首页。

## 第四部分：里程碑拆分

### M1（首个实现计划的全部范围）：使用中的状态引导

仅包含方向 A：

1. `PhotoStatusCard` / `QuestionRowCard` 统一组件，整卡可点，语义五色沿用。
2. 「本周」页分区重排 + 顶部「下一步」摘要条（计数全部来自 `store.state` 真实派生，**无进度即无百分比**；卡片聚合文案严格按 5.0 节规则，禁止照搬现有 `pending == 0 ⇒ 已全部确认` 推断）。
3. 题目详情页重排：原图证据 → 识别内容 → 需核对项 → 状态主操作区（每状态一个主按钮：确认/放行/重试/去复盘/跳过）；坐标等技术指标折叠。
4. 已确认出口可点（详情页 + 列表行直达复盘）。
5. 空/慢/部分成功/离线恢复/失败重试文案与状态（见第五部分状态表与错误分类）。**R1 强化**：`lastError` 是广义请求/缓存错误，不等于离线——必须区分设备离线、请求超时、服务暂不可用、配对失效、媒体读取失败；无法归类时显示「进度暂未更新」并保留缓存与重试入口，**禁止把所有卡片标记为任务失败**。
6. 视觉基础设施：移除强制浅色，Palette 改为动态颜色（light/dark 双套值）；全部状态同时用「图标 + 文字 + 颜色」三通道；Dynamic Type 全页面校验；VoiceOver 状态朗读；Reduce Motion 下复盘点选推进改为即时切换；Liquid Glass 仅用于导航控件且按系统版本适配（iOS 26+ 用系统玻璃 Tab 外观，18–25 回落标准材质；题干/照片/卡片**不铺玻璃**）。

**M1 需要的服务端调整：无。** 所有状态文案与计数均可从现有 `RecognitionJob/RecognitionQuestion` 契约派生（`docs/mobile-recognition-api.md` v1 契约不变）。

### M2（本轮只定义边界与接口，不实现、不声称已支持）：语音纠错

**定位**：纠正**识别转写错误**（题干文字、图示说明的转写），入口与键盘编辑同一修正面板。绝不把学生原作的错误计算「修正」为正确解——`student_work`/`correction` 等来源记录只允许修正**转写保真**（把识别错的字改对），模型被明确禁止改动其数学内容；`textFidelity` 门禁语义（`CROP_COMPLETENESS.md` 30–39 行）保持。

**流程**：题目详情「有改动？点这里修正」→ 修正面板（语音/键盘同面板切换）→ 语音：按住说话 → 端上 ASR 出文字稿（学生可编辑）→ 发送修正请求 → 返回修改前后对照预览 → 学生明确「接受」才生效；歧义时模型反问（一次一个澄清问题）；任何时刻可取消。

**接口草案（服务端新增，需真实模型评测后才启用）**：
`POST /v1/recognitions/{jobId}/questions/{questionId}/correct`，body 含 `revision`（乐观锁）、`instruction`（ASR 文字稿）、`clientRequestId`（UUID 幂等键）。响应为「建议修订包」：改动字段的 before/after diff，或 `clarify` 反问。学生接受后走第二个确认调用（带 revision + 修订包 ID）落库：证据 `version` 不变、`question.revision` 递增、**该项既有 verification/crop 检查全部失效**（`CROP_COMPLETENESS.md` 47–49 行：证据变化使检查与诊断失效），回到待核对状态重新校验。客户端本地保存修正历史（每条含文字稿、diff、时间、可撤销到同一 revision 链上的任意点）。

**隐私与管线节点（必须写进实现计划）**：麦克风权限 `NSMicrophoneUsageDescription` + `SFSpeechRecognizer` 授权，`requiresOnDeviceRecognition = true`——**原始音频不出设备**；只有文字稿随修正请求上服务器；发送时机仅在学生点「生成修改建议」时；录音文件不落盘（内存缓冲，说完即弃）；文字稿仅存于本地修正历史，学生可逐条/全部删除。服务端节点：修正模型（新配置项，复用北京百炼端点，缺配置 fail-closed 不降级）；**ASR 不上云**、不经百炼语音模型。费用：每次「生成建议」一次模型调用，界面上明示「这次修正会请求一次 AI」；超时沿用 15s 检查/180s 提交的通道语义并新增修正专用上限（建议 60s）。幂等与冲突：`clientRequestId` 去重；revision 不匹配返回 409，客户端刷新后重显最新内容，不覆盖别人/别处的更新。失败永远保留键盘手动路径。

**ASR 可用性（R1 强化，未实测不承诺）**：`SFSpeechRecognizer` 端上模式在初三学生真实中文口音、语速、嘈杂环境下的识别质量与各机型可用性**均未实测**；键盘编辑与语音在同一修正面板，键盘路径永远可用，ASR 不可用/识别失败时如实提示并落在键盘路径，不伪造语音能力。启用前必须真机实测，单一样本不能证明可用。

### M3（本轮只定义边界与接口）：错题归类

**数据基础**：`RecognitionEvidence.subject/chapter/knowledgeTags` 已由服务端抽取（`Recognition.swift` 79–81 行），客户端丢弃了结构（`StudyProblem.topic` 平铺）。

**设计**：`StudyProblem` 新增结构化字段 `subject`、`chapter`、`knowledgePoints: [String]`（`StudyState` 升 schemaVersion 3，`decodeIfPresent` 兼容旧档——沿用 `LocalRecognitionTask.ownedServiceId` 的既有兼容模式）。同义标签规范化用「存储规范值 + 显示别名」表（沿用 `ReflectionOptions.chineseTitles` 模式），**规范表放服务端**随证据下发，客户端不硬编码词表；首版表由人工维护，不让模型在确认后擅自改标签。一题多知识点沿用数组（已支持）；**不重复收题**：按规范化题干指纹提示「可能是同一道题」，学生手动决定合并/保留各自，绝不自动合并。模型没把握的标签进「待归类」组，学生可改；学生改标签属本地学习标注，**不改动证据、不触发检查失效**（标签不参与打印与证据指纹——此边界须经审查确认）。「复盘」与「练习包」按 科目→章节→知识点 分组展示，组级显示「N 道待复盘 / M 道待重做」聚合；家长侧仍只有聚合统计，不新增明细。

**M3 服务端调整**：规范标签表下发（可选；缺表时客户端原样展示原始标签，功能降级但不阻断）。**数据回退风险**：v3 状态文件不能被旧版 App 读取——现有加载器对 `schemaVersion != 2` 抛 `unsupportedState` 且**不覆盖数据**（fail-closed，安全），降级体验是「旧版打不开新档但数据保留」，须在发布说明中写明。

### 5.0 状态聚合规则（精确定义，R1 新增）

现有 `ThisWeekView.swift` 155–157 行「无 ready/needs_check ⇒ 已全部确认」的推断**不充分**，M1 必须按下表精确聚合，禁止照搬：

| 情形 | 聚合结果 | 说明 |
|---|---|---|
| 候选数为零（job 完成但 questions 为空） | 「这张照片没有发现可识别的题目」 | 绝不显示「全部已确认」 |
| 全部 skipped | 「全部已跳过」 | 只可查看；恢复需未来接口（见 2.1） |
| confirmed + failed 混合 | 「X 道已确认 · Y 道没识别成功」 | 主操作：重试失败题（只影响失败项） |
| ready/needs_check + processing 混合 | 「可以开始核对：X 道已就绪 · 还有 Y 道识别中」 | **处理中不阻塞**：可先核对已就绪题，不能全页等待 |
| 出现未知 status 值 | 「状态需核对」 | 沿用现有 default 文案，不猜测 |
| 题目数 > 0 且全部 confirmed | 「全部已确认」 | 唯一允许显示该文案的情形 |

计数措辞：「已处理 X/N」中的已处理**包含失败题**，文案必须写「已处理」而非「已成功」；needs_check 计入「待你核对」，不叫「可用」。

## 第六部分：验收标准（M1，可亲手验证；不是单测数量）

1. **整卡可点**：真机「本周」页每张照片卡的任意位置（缩略图、状态、空白处）点击都进入正确目的地（待确认→第一道待确认题；失败→重试详情；已确认→题目列表）。目检 + 录屏。
2. **三态走查**：一次会话内制造 3 张照片——正常、故意模糊导致失败/待核对、上传中途断网——三种颜色与三句不同的「下一步」同时出现在首页，且每个主操作真实可用。
3. **无伪造进度**：识别中页面只出现「已处理 X/N 道」或「正在识别」，全文搜索 UI 无百分比（上传除外，上传是真实字节进度）。
4. **重新打开，不新增动作（R2 重写）**：识别中强杀 App 重进——照片卡先显示缓存内容并标注最后更新时间，云端刷新返回后再显示真实状态（处理中/已完成/失败）。验收判据：重开过程客户端**只发起只读查询（GET job/health）**——**无由重开动作触发的新增 submit/retry/重复模型调用，通过请求来源与任务链关联核实**；已有后台任务的自然推进（包括其正常产生的新 usage）属于预期，不计入违例。仅当云端任务自身确实为 `interrupted`（服务器判定，非客户端推断）时才出现「继续识别」。
5. **深色/浅色**：系统切换深浅色，全部页面无白底文字消失、无对比度坍塌；`preferredColorScheme(.light)` 已移除。
6. **动态字号**：系统字号调至最大，「本周」与题目详情的主按钮、状态徽标不截断、不重叠。
7. **VoiceOver**：从首页到确认一道题全程只听不看的可完成性走查——每卡朗读出「照片 2，待你确认 3 道题，按钮」级语义。
8. **Reduce Motion**：开启后复盘点选无位移动画，功能不变。
9. **回归**：既有确认门禁不弱化——未看原图不能确认、图示缺失阻止练习包、反思仍须学生提交（对应既有 UI 测试 `StudentJourneyTests` 等全绿）。
